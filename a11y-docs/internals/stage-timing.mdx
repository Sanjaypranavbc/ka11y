## Why this exists

The combined audit emits three timing artefacts. They overlap by design, each
answering a different question:

| File | Granularity | Best for |
|------|-------------|----------|
| `a11y-python/logs/run_timings.log` | One markdown block per run | "How long did this audit take?" |
| `<output_dir>/crawler_timings.log` | One row per crawler invocation per run | "Was the crawl the bottleneck?" |
| `a11y-python/logs/timings/<run_id>.jsonl` | One row per **(page, stage, sub_stage, rule)** step | "Which page on which rule cost us 4 s?" |
| `a11y-python/logs/timings/<run_id>.summary.log` | Human-readable rollup of the JSONL | Quick triage without parsing JSON |

The JSONL is machine-parseable so you can graph it, diff between runs, or feed
it into a notebook. The summary log is meant for tailing during an investigation.

## Where the files land

```
a11y-python/
└── logs/
    ├── run_timings.log              ← existing aggregate log
    └── timings/
        ├── <run_id>.jsonl           ← one row per step
        └── <run_id>.summary.log     ← rollup written at end of run
```

Override the directory with `A11Y_STAGE_TIMING_DIR`. Disable both files
(without touching the other timing logs) with `A11Y_STAGE_TIMING_DISABLE=1`.
See [Environment](/deployment/environment).

## JSONL row schema

Each line in `<run_id>.jsonl` is a JSON object:

```json
{
  "ts":          "2026-05-29T10:42:18.731+00:00",
  "run_id":      "a11y-abc123",
  "page_url":    "https://example.com/child",
  "depth":       1,
  "stage":       "image_audit",
  "sub_stage":   "ocr_converter",
  "rule":        "1.4.3",
  "duration_ms": 123.4,
  "item_count":  42,
  "status":      "ok",
  "error":       null,
  "extra":       { "input_count": 86 }
}
```

| Field | Type | Always present | Meaning |
|-------|------|----------------|---------|
| `ts` | ISO 8601 string | Yes | Wall-clock timestamp at row write (millisecond precision, UTC) |
| `run_id` | string | Yes | The audit job ID; same value as the JSONL filename |
| `page_url` | string \| null | No | The page this step is attributable to. `null` for stage-level rows |
| `depth` | int \| null | No | BFS depth of `page_url` (0 = entry URL) |
| `stage` | string | Yes | Top-level stage (`image_audit`, `form_audit`, `rendered_layout_audit`, etc.) |
| `sub_stage` | string \| null | No | Fine-grained phase inside a stage. See table below |
| `rule` | string \| null | No | WCAG SC the row attributes to (e.g. `1.4.3`). `null` for non-rule work |
| `duration_ms` | float | Yes | Elapsed milliseconds for this step |
| `item_count` | int \| null | No | Stage-specific work-item count (images scanned, findings produced, …) |
| `status` | string | Yes | `ok`, `error`, or `warning` |
| `error` | string \| null | No | Stringified exception (truncated to 200 chars) when `status="error"` |
| `extra` | object | Yes | Free-form per-stage details; never depended on for parsing |

### Sub-stages emitted today

| `stage` | `sub_stage` | When |
|---------|-------------|------|
| `image_audit` | `ocr_scan` | Around `OCRPreprocessing.scan_directory()` |
| `image_audit` | `ocr_save_reports` | Around `TextClassification.save_reports()` |
| `image_audit` | `ocr_converter` | Per-rule, per OCR converter call (1.4.3, 1.4.6) |
| `image_audit` | `image_audit_converter` | Per-rule, per image-audit record converter (1.1.1, 4.1.2, 1.4.5, 1.4.11) |
| `image_audit` | `image_crawl_page` | Per page visited by the image crawler |
| `image_audit` | `image_crawl_budget` | One row at crawl end with `extra.discovered` / `audited` / `clipped` |
| _any stage_ | _omitted_ | The auto-recorded row written by `_stage_complete` / `_stage_error` |
| `axe_core` | `page_navigate` | Node — `page.goto()` per crawled page |
| `axe_core` | `inject_axe` | Node — axe-core script injection + locale config |
| `axe_core` | `axe_run` | Node — `axe.run()` against the page |
| `axe_core` | `custom_checks` | Node — `runAll()` over custom check plugins |
| `axe_core` | `result_mapping` | Node — `mapResultsFlat` + `mapCustomResultsFlat` |

Every other stage in `_run_python_stages_combined` (`form_audit`,
`pause_stop_hide_audit`, `text_spacing_audit`, `rendered_layout_audit`,
`media_audit`, `sensory_audit`, `pipeline`) gets a single auto-recorded row at
completion — drilling further down inside those stages is a future extension.

## Summary log format

`<run_id>.summary.log` is rewritten at the end of every run by `runner.py`:

```
# a11y stage timing summary — run_id=a11y-abc123
# generated: 2026-05-29T10:50:02.110+00:00
# rows: 412    summed duration: 84.31s
# note: summed != wall time (stages run concurrently via asyncio.gather)

## Stage totals (sum across all pages)
stage                               total_s    count    mean_ms     max_ms
------------------------------------------------------------------------
image_audit                           42.10      318      132.4    4180.0
rendered_layout_audit                 21.04        7     3005.7   12480.0
form_audit                             4.10        3     1366.6    2400.0
pipeline                               3.91        1     3910.0    3910.0
…

## Per-page breakdown

### https://www.kao.com/jp/    (total 38.42s)
  stage                          total_s    count             top_rule     rule_s
  --------------------------------------------------------------------------------
  image_audit                      30.10      210                1.4.3       18.40
  pipeline                          3.91        1                1.1.1        3.91
  …

### https://www.kao.com/global/en/worldwide.html    (total 19.88s)
  …
```

The `top_rule` column is the heaviest WCAG SC for each (page, stage) cell.
"summed != wall time" is highlighted at the top because audit stages run
concurrently via `asyncio.gather` — adding rows is informative but the real
wall time is in `run_timings.log`.

## How rows are emitted

- **Auto-recorded** at every stage boundary by `_stage_complete` / `_stage_error`
  in `a11y/api/v1/combined/stage_events.py`. Every stage gets a per-stage row
  for free — adding a new stage does not require any timing wiring.
- **Node engine rows are mirrored back** through the HTTP response. Python's
  `_call_node_flat` forwards the `job_id` as `jobId` in the request body; Node
  builds a per-request `StageTimings` collector (`a11y-node/src/utils/stageTimings.js`),
  wraps `page_navigate` / `inject_axe` / `axe_run` / `custom_checks` / `result_mapping`
  in each visited page, and returns the rows as `timings: [...]` alongside
  `findings`. Each row is then appended to the shared JSONL with
  `extra.source = "node"` so you can tell engines apart. Node and Python share
  no volume — the response payload is the channel.
- **Manual per-page / per-rule rows** are added with the helper context managers
  in `a11y/utils/stage_timing.py`:

  ```python
  from a11y.utils import stage_timing

  async with stage_timing.time_stage_async(
      job_id,
      "image_audit",
      sub_stage="ocr_converter",
      rule="1.4.3",
      page_url=current_page_url,
      extra={"input_count": len(ocr_results)},
  ):
      findings.extend(converter(ocr_results, url, page_by_filename=page_by_filename))
  ```

  A sync `time_stage(...)` and a direct `record(...)` are also exposed for
  hand-instrumented call sites (e.g. inside the image crawler per-page loop).
- **Summary file** is rendered by `stage_timing.emit_summary(run_id)`, called
  once from `runner.py` after `log_run_timing(...)` on both the success and
  failure paths.

## Safety guarantees

- Every write is wrapped in `try / except` — a logging failure must never abort
  an audit. Failures are logged at WARNING via the standard a11y logger and
  swallowed.
- Per-file `threading.Lock` so concurrent stages can not interleave rows.
- `run_id` is sanitised before it is used in a path (only alphanumerics,
  `-`, `_`, `.`) so a malicious value cannot escape the timings directory.

## Verifying the depth fix

After the D-1 / D-3 fixes (see internal notes), the same child page audited as
a sub-page of a parent should report a finding count close to the count it
reports when audited directly. To check this on your own deployment:

```bash
cd a11y-python
poetry run python scripts/verify_depth_fix.py \
    --a1 https://www.example.com/parent \
    --a2 https://www.example.com/parent/child
```

The script posts both audits concurrently, polls until each completes, and
prints per-page finding counts plus the `a2-as-child : a2-direct` ratio. The
two timing files for each run are written to `logs/timings/<run_id>.{jsonl,summary.log}`
— tail them in another shell while the audits run.

## Disabling

```bash
# Skip all stage-timing writes; existing crawler_timings.log + run_timings.log are unaffected.
A11Y_STAGE_TIMING_DISABLE=1
```

The flag is read on every write, so it can be toggled per-run without
restarting the service.
