## What it checks

WCAG 4.1.3 requires that in content implemented using markup languages, status messages can be programmatically determined through role or properties such that they can be presented to the user by assistive technologies without receiving focus.

a11y uses heuristics to identify dynamic content regions and verify if they are properly marked as live regions.

## How it works

The Node engine performs a structural scan of the page to identify status-related patterns:

1.  **Live Region Inventory**: Scans the DOM for elements with `aria-live` or specific ARIA roles: `status`, `alert`, `log`, `timer`, `marquee`.
2.  **Dynamic Context Detection**: Identifies regions likely to receive dynamic updates using multi-language keywords in IDs and classes:
    *   **Search Results**: `results`, `検索結果`, `search-count`.
    *   **Shopping Cart**: `cart-count`, `basket-total`.
    *   **Notifications**: `toast`, `snackbar`, `alert-box`, `badge`.
3.  **Atomic Validation**: For `role="alert"`, the auditor checks if `aria-atomic="true"` is present (best practice for ensuring the whole message is read).
4.  **Inline Validation Detection**: Checks for form fields with `aria-invalid="true"` and verifies if the associated error message is within a live region.

## Status Semantics

*   **FAIL**: Strong evidence of dynamic content (like a search result counter) that is not marked as a live region.
*   **PASS**: All detected dynamic regions are properly marked with appropriate ARIA roles or `aria-live`.
*   **INCOMPLETE**: Heuristic signals of status UI (e.g., "Toast" containers) that lack ARIA semantics and require manual verification.

## Common violations

| Violation | Example |
|-----------|---------|
| Silent updates | A "Items in cart: 3" counter that updates via AJAX but has no `aria-live` attribute. |
| Inaccessible alerts | A success message that appears at the top of a form but is not announced to screen readers. |
| Missing aria-atomic | An alert that only announces the *changed* part of a message, losing context. |

## Suggested fix

Use the appropriate ARIA role for all dynamic status updates.

```html
<!-- Recommended: status role for non-critical updates -->
<div role="status">
  3 results found.
</div>

<!-- Recommended: alert role for critical errors -->
<div role="alert" aria-atomic="true">
  Invalid username or password.
</div>

<!-- For e-commerce counters -->
<span class="cart-count" aria-live="polite">
  Cart (5 items)
</span>
```

## Known limitations

*   **Snapshot-only**: Since this is a static scan, it cannot verify if a message is *actually* announced when an event occurs. It only checks if the *container* is ready to be announced.
*   **Async Updates**: Status messages that are both injected *and* removed via JavaScript between audits may be missed.
