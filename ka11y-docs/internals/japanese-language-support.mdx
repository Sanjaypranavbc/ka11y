## Summary

ka11y supports Japanese audits end-to-end: the `lang` parameter flows through both engines, finding text is localised via `i18n/rules.yml` + locale overlay, and some NLP-backed rules use a Japanese spaCy model. However, **NLP-dependent rules produce a higher false-positive/false-negative rate on Japanese pages** than on English pages due to tokenization limitations, vocabulary gaps, and `lang` attribute drift.

DOM-structural, rendered-layout, and contrast rules are unaffected — they operate on computed style and bounding boxes and produce equivalent quality for all languages.

## What is partially covered

### 1.3.3 Sensory Characteristics

**File:** `ka11y-python/ka11y/accessibility/rules/non_text/sensory_auditor.py`

The auditor uses spaCy's `ja_core_news_sm` (12 MB) to tokenize and analyse instructional text. Three structural problems limit accuracy:

#### Problem 1 — Token boundary errors on web text

`ja_core_news_sm` is trained on newswire. Japanese web copy uses casual register, katakana loan words, and ASCII-mixed text (e.g. `"右のボタンをクリックしてください"`). The model mis-tokenizes these — for example splitting `クリックして` into `クリック` + `して` but misclassifying `して` as a content word rather than a conjunctive particle.

`_remaining_label_words` removes tokens by set-membership lookup in `SENSORY_WORDS`. If tokenization is wrong, the lookup fails and sensory-only instructions are not flagged (false pass).

#### Problem 2 — `SENSORY_WORDS` is English-only

The sensory vocabulary has no Japanese entries. A sentence like `"赤いボタンを押してください"` ("Please press the red button") contains only a colour reference (`赤い`) and a direction-of-action, which is a textbook SC 1.3.3 failure — but because `"赤い"` is not in `SENSORY_WORDS`, it survives the filter as a content word and produces a false pass.

Missing Japanese sensory terms:

| Japanese | Romaji | English |
|---|---|---|
| 右 | migi | right |
| 左 | hidari | left |
| 上 | ue | top / above |
| 下 | shita | bottom / below |
| 赤い / 赤 | akai / aka | red |
| 青い / 青 | aoi / ao | blue |
| 黄色 | kiiro | yellow |
| 緑 | midori | green |
| 丸い / 丸 | marui / maru | round / circle |
| 四角 | shikaku | square |
| 点滅 | tenmetsu | flashing |
| 音声 | onsei | audio / sound |
| 形 | katachi | shape |
| 色 | iro | color |
| 位置 | ichi | position / location |
| 大きい | ookii | large |
| 小さい | chiisai | small |

#### Problem 3 — CJK character-class stripping vs. morpheme filtering

The JA fallback in `_remaining_label_words` strips characters via a Unicode range regex instead of filtering by POS tag. This removes content words and structural particles alike, producing inconsistent results. A sentence that mixes kanji (sensory) with hiragana particles loses its sensory kanji but retains the (now meaningless) particle text as a residual "content" token.

### 1.1.1 Non-text Content — OCR path

PaddleOCR and EasyOCR are used for alt-text validation against image content. Japanese-specific gaps:

| Issue | Impact |
|---|---|
| Vertical text (縦組み / tategumi) | OCR reads columns left-to-right; characters are merged or swapped |
| Half-width katakana (`ｶﾀｶﾅ`) | Treated as ASCII symbols; not matched against JA keyword patterns |
| Fonts below 12 pt | Misread rate increases substantially; small kanji strokes are dropped |
| Mixed kanji + kana + ASCII | Model confidence drops below threshold; region is skipped |

## `lang` attribute drift

**This is the single highest-impact bug for Japanese audits.**

Language routing in both engines is driven by `<html lang="...">`. When a page declares `lang="en"` but contains Japanese body content (extremely common on corporate microsites and bilingual pages), the English spaCy pipeline is loaded and JA text is processed character-by-character as unknown tokens.

`sensory_auditor.py` current logic (simplified):

```python
lang = page_snapshot.lang or "en"
if lang.startswith("ja"):
    nlp = get_spacy_model("ja_core_news_sm")
else:
    nlp = get_spacy_model("en_core_web_sm")
```

This single `startswith("ja")` check misses:
- `lang="en"` pages with JA text blocks that have inner `lang="ja"` spans
- `lang="ja-JP"` variants (correctly handled — `startswith` passes)
- Pages with no `lang` attribute at all (default to English)

## Recommended fixes — priority order

### Priority 1 — `lang` drift fix (fasttext-langid)

Replace the single-page language check with per-element language detection:

```python
import fasttext
_lid_model = fasttext.load_model("lid.176.ftz")  # 917 KB model

def detect_lang(text: str) -> str:
    if len(text) < 10:
        return "en"  # too short to classify
    labels, _ = _lid_model.predict(text.replace("\n", " "), k=1)
    return labels[0].replace("__label__", "")
```

Call `detect_lang(element.inner_text)` for each instructional sentence before dispatching to the spaCy pipeline. Cache per unique text to avoid repeated inference.

---

### Priority 2 — Upgrade `ja_core_news_sm` → `ja_core_news_lg`

```bash
python -m spacy download ja_core_news_lg
```

Update model loading in `sensory_auditor.py`:

```python
JA_MODEL = os.getenv("KA11Y_JA_SPACY_MODEL", "ja_core_news_lg")
```

The large model includes contextual word vectors and achieves 94%+ POS accuracy on web-register text. Load lazily on first JA request; the model is ~400 MB but is cached in process memory.

---

### Priority 3 — SudachiPy morpheme-level stop-word filtering

Replace the CJK character-class regex strip with SudachiPy tokenization:

```python
from sudachipy import tokenizer, dictionary

_sudachi = dictionary.Dictionary().create()

DISCARD_POS = {"助詞", "助動詞", "記号", "接続詞", "感動詞"}

def japanese_content_words(text: str) -> list[str]:
    morphemes = _sudachi.tokenize(text, tokenizer.Tokenizer.SplitMode.C)
    return [
        m.dictionary_form()
        for m in morphemes
        if m.part_of_speech()[0] not in DISCARD_POS
    ]
```

Use this in `_remaining_label_words` when `lang == "ja"`.

### Priority 4 — Expand `SENSORY_WORDS` with Japanese

In `sensory_auditor.py`, add to the `SENSORY_WORDS` set:

```python
SENSORY_WORDS_JA = {

SENSORY_WORDS = SENSORY_WORDS_EN | SENSORY_WORDS_JA
```

### Priority 5 — Half-width katakana normalization

Add NFKC normalization as the first step in all text-processing paths (both Python and Node):

```python
# Python
import unicodedata
text = unicodedata.normalize("NFKC", text)
```

```javascript
// Node
text = text.normalize("NFKC");
```

This converts `ｶﾀｶﾅ` → `カタカナ`, `Ａ` → `A`, and `１` → `1`, ensuring half-width variants match keyword patterns and OCR patterns consistently.

### Priority 7 — OCR: vertical text fallback

When PaddleOCR confidence for a text region is below 0.6, add a Tesseract vertical-text fallback:

```python
import subprocess

def ocr_with_vertical_fallback(image_path: str, lang: str) -> str:
    result = paddle_ocr(image_path, lang=lang)
    if result.confidence < 0.6 and lang == "ja":
        # Try vertical PSM
        out = subprocess.run(
            ["tesseract", image_path, "stdout", "-l", "jpn_vert", "--psm", "5"],
            capture_output=True, text=True
        )
        if out.returncode == 0:
            return out.stdout
    return result.text
```

## Testing JA coverage

A minimal test fixture for `sensory_auditor.py` JA coverage:

```python
@pytest.mark.parametrize("text,should_fail", [
    ("右のボタンを押してください", True),   # colour/direction only
    ("送信ボタンを押してください", False),  # non-sensory label
    ("赤いリンクをクリックしてください", True),  # colour only
    ("次へボタンをクリックしてください", False),  # directional but has "next"
])
def test_sensory_ja(text, should_fail):
    result = check_sensory_instruction(text, lang="ja")
    assert result.is_failure == should_fail
```

For Node, add JA entries to the existing `link-purpose` test fixtures in `ka11y-node/src/custom-checks/__tests__/`.
