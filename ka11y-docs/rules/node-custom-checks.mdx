`ka11y-node` ships **24** custom checks in addition to raw axe-core. They run inside the same `axe_core` stage, so they are returned together with axe-core findings rather than as a separate API stage.

These checks exist for three reasons:

- to cover WCAG criteria that axe-core does not attempt
- to add stronger heuristics on top of axe-core for criteria ka11y wants to surface earlier
- to exercise live page behavior such as focus, keyboard flow, and input-triggered context changes

## Status semantics

The Node custom checks are intentionally conservative:

- `fail` is used for high-confidence evidence only
- `pass` is used when the criterion is clearly not applicable or there is strong positive evidence
- `incomplete` is used when a single-page heuristic cannot prove a WCAG failure

Current examples of conservative behavior:

- `1.2.1` does not treat `<track>` alone as a transcript for audio-only content
- `3.1.6` pronunciation heuristics do not auto-fail a CJK page just because ruby is absent
- `3.2.6` consistent-help stays `incomplete` on a single page because cross-page consistency is a site-level property
- `2.4.8` only passes on visible location indicators; sitemap or JSON-LD alone stay `incomplete`
- `4.1.3` no longer fails a page just because forms exist without live regions

## Static checks

| WCAG SC | Rule ID | Focus | Typical behavior |
|---------|---------|-------|------------------|
| `1.2.1` | `custom-audio-transcript` | Audio-only transcript evidence near `<audio>` elements | `incomplete` unless transcript evidence is clear or the page has no audio |
| `1.3.2` | `custom-meaningful-sequence` | CSS reordering via flex, grid, float, and `order` | Usually `incomplete` because visual-vs-DOM intent is heuristic |
| `1.3.4` | `custom-orientation` | JS lock calls, manifest/meta restrictions, CSS orientation hiding, forced rotation | Mix of `fail` and `incomplete`; Python rendered auditor remains the primary orientation engine |
| `1.4.1` | `custom-use-of-color` | Inline links that appear distinguishable by color alone | `fail` on strong inline-text cases |
| `1.4.5` | `custom-images-of-text` | Heuristic text-in-image detection from DOM attributes and CSS background hints | Heuristic preflight; Python OCR-backed image audit remains primary |
| `2.1.4` | `custom-character-key-shortcuts` | Single-character keyboard shortcuts in inline handlers and scripts | Usually `incomplete` unless the shortcut pattern is explicit |
| `2.4.5` | `custom-multiple-ways` | Search, sitemap, nav, breadcrumb, and table-of-contents presence | Often `incomplete` on single pages |
| `2.4.8` | `custom-location` | Breadcrumbs, `aria-current`, active nav items, current-step cues | `pass` on visible cues, `incomplete` on weaker hints |
| `2.4.9` | `custom-link-purpose` | Generic link text such as “click here” or “more” | `fail` on clear ambiguous text |
| `2.5.2` | `custom-pointer-cancellation` | Action handlers that fire on down events without an up/cancel path | Usually `incomplete` unless the inline action is explicit |
| `2.5.7` | `custom-dragging-movements` | Drag-and-drop UI without a detectable single-pointer alternative | Usually `incomplete` unless alternatives are clearly absent |
| `3.1.6` | `custom-pronunciation` | Ruby/furigana heuristics for CJK content and sections | `incomplete` unless clearly not applicable |
| `3.2.6` | `custom-consistent-help` | Help/contact/support mechanisms on the page | `incomplete` because cross-page order and location need site-level evidence |
| `3.3.3` | `custom-error-suggestion` | Whether detected error messages include correction guidance | `fail` on terse messages like “Invalid” with no guidance |
| `3.3.4` | `custom-error-prevention` | Review/confirm safeguards for legal, financial, or destructive forms | `fail` on strong no-safeguard cases |
| `3.3.7` | `custom-redundant-entry` | Repeated personal-data fields within the same likely process | `fail` or `incomplete` depending on confidence and reuse signals |
| `3.3.8` | `custom-accessible-auth` | CAPTCHA alternatives, paste blocking, cognitive tests, passkey alternatives | `fail` on strong evidence; scoped per auth form |
| `4.1.1` | `custom-html-parsing` | Duplicate ids, broken ARIA references, and orphaned `label[for]` links | `fail` on clear parsing-affecting issues |
| `4.1.3` | `custom-status-messages` | Live-region heuristics for dynamic updates, forms, counters, and notifications | `fail` only on strong dynamic-update cases; many page-level signals stay `incomplete` |

## Interactive checks

| WCAG SC | Rule ID | Focus | Typical behavior |
|---------|---------|-------|------------------|
| `2.1.2` | `custom-keyboard-trap` | Tab, Shift+Tab, arrow-key, and iframe trap patterns | `fail` on strong escape failures, `incomplete` on weaker widget traps |
| `2.4.7` | `custom-focus-visible` | Visible focus style after real focus movement | `fail` on sampled focusable elements with no visible change |
| `2.4.13` | `custom-focus-appearance` | Focus-indicator area and contrast | `fail` on measurable area/contrast misses |
| `3.2.1` | `custom-on-focus` | Context changes triggered purely by focusing an element | `fail` on navigation or SPA route changes on focus |
| `3.2.2` | `custom-on-input` | Context changes triggered by changing an input value | `fail` on navigation or route changes after input/change interaction |
