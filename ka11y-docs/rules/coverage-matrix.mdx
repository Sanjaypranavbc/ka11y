This page documents, for every implemented rule in `ka11y-python` and `ka11y-node`, which W3C WCAG 2.2 Techniques are actually detected by the code path versus those that are partially detected or missed. Use it to understand automation limits before interpreting audit results.

<Info>
  See the companion [WCAG Rules Overview](/rules/overview) for the high-level axe-core vs Python coverage map. This page zooms in on individual techniques.
</Info>

## Legend

| Status | Meaning |
|---|---|
| **Covered** | Reliably detected by the implemented logic. |
| **Partial** | Detection exists but with false positives or false negatives; review output manually. |
| **Missed — automatable** | Could be detected; gap that can be closed with additional code. |
| **Missed — judgment** | Requires human judgment or visual interpretation. |
| **Missed — interactive** | Requires a full browser-interaction simulation that is not yet wired. |

## 1.1.1 Non-text Content
**Engine:** `ka11y-python` pipeline (`policy_1_1_1.py` + `alttext.py` + OCR + image classifier) plus `ka11y-node` `background-image-content.check.js` for CSS background images.

| Technique | Kind | Status |
|---|---|---|
| H37 `alt` on `<img>` | Sufficient | Covered |
| H67 Null `alt` on decorative | Sufficient | Covered |
| ARIA6 / ARIA10 | Sufficient | Covered |
| H36 `alt` on `<input type="image">` | Sufficient | Partial |
| H53 `<object>` fallback content | Sufficient | Missed — automatable |
| H2 Adjacent text + image | Sufficient | Missed — automatable |
| F3 CSS background-image carrying information | Failure | Partial (Node `custom-background-image-content`) |
| F20 `alt=""` on informative | Failure | Covered |
| F30 Filename / placeholder alt | Failure | Covered |
| F38 / F39 Decorative mis-marked | Failure | Covered |
| F65 Missing alt + all alternative name sources | Failure | Covered |
| F71 Emoji/symbol without text alt | Failure | Missed — automatable |

**Known limitations**
- 3-character OCR token floor causes false negatives on valid 2-letter labels (e.g. "UI").
- OCR matching is literal — semantic synonyms (alt "Look up" vs OCR "Search") fail.
- CSS `background-image` detection is **filename-heuristic only** — it does not OCR the background pixels. Backgrounds whose filenames do not contain decoration or text keywords pass through the "needs review" bucket; real image content is not analysed.
- Classifier misclassification propagates: a logo labelled as `informative` bypasses logo-keyword enforcement.

## 1.3.3 Sensory Characteristics
**Engine:** `ka11y-python/sensory_auditor.py` (spaCy EN + JA).

| Technique | Kind | Status |
|---|---|---|
| G96 Non-sensory identifier | Sufficient | Covered |
| F14 Identify content only by shape/location | Failure | Covered (EN) / Partial (JA) |
| F26 Graphical symbol alone | Failure | Missed — requires visual grounding |

**Japanese-specific limitations**
- `ja_core_news_sm` (12 MB model) tokenizes web-register Japanese at ~91% POS accuracy. Mixed kanji/kana/ASCII text common on Japanese sites causes token boundary errors that propagate to false passes.
- `_remaining_label_words` uses CJK character-class stripping (regex) rather than morpheme-level stop-word filtering — particles and postpositions (は, が, を) can survive the filter as phantom "content" words.
- `SENSORY_WORDS` is English-primary. Japanese sensory terms (`右`, `左`, `上`, `下`, `赤い`, `青い`, `丸い`, `点滅`, `形`, `色`) are not included — sensory-only JA instructions pass without flagging.
- When `<html lang="en">` but body text is Japanese, the English spaCy pipeline is used and JA tokens become unknowns.

# Language Support Limitations

## Japanese / CJK

<Warning>
  Japanese language support is **partial** across multiple rules. Audits of Japanese-language pages will produce findings but with a higher false-positive and false-negative rate than English-language audits.
</Warning>

| Rule | EN quality | JA quality | Primary gap |
|---|---|---|---|
| 1.3.3 Sensory Characteristics | Strong | Weak | spaCy `sm` model + no JA sensory vocab |
| 2.4.9 Link Purpose | Strong | Partial | Static keyword list — novel JA patterns missed |
| 2.4.5 Multiple Ways | Strong | Partial | JA breadcrumb / nav patterns incomplete |
| 3.2.6 Consistent Help | Strong | Partial | JA help-link taxonomy incomplete |
| 3.3.3 Error Suggestion | Strong | Partial | JA suggestion-text pattern matching only |
| 3.3.4 Error Prevention | Strong | Partial | JA financial/legal keyword coverage |
| 1.1.1 Non-text Content (OCR) | Strong | Partial | Vertical text, half-width kana, small fonts |

### Why Japanese coverage is partial

**Tokenization:** Japanese has no word spaces. The `ja_core_news_sm` spaCy model (used in `sensory_auditor.py`) tokenizes via a SudachiPy-derived dictionary. On web-register text (casual, katakana loan words, ASCII-mixed) the model produces token boundary errors. These propagate to incorrect label-word comparisons in NLP-based checks.

**`lang` attribute drift:** Language routing uses `<html lang="...">`. Mixed-language pages that declare `lang="en"` but contain Japanese body text load the English pipeline — JA characters are processed as unknown tokens.

**Vocabulary gaps:** `SENSORY_WORDS`, `GENERIC_UI_NOUNS`, and `PURPOSE_WORDS` in `sensory_auditor.py` are English-primary. There is no Japanese sensory vocabulary. The CJK fallback strips characters by Unicode range rather than morpheme POS tag, causing particles and postpositions to survive as phantom content words.

**OCR gaps:** EasyOCR's JA model struggles with vertical text (tategumi), fonts below 12 pt, and half-width katakana (`ｶﾀｶﾅ`). PaddleOCR performs better when `lang=ja` is explicitly configured.

**Node keyword lists:** JA keyword lists in Node custom checks (`link-purpose.check.js`, `consistent-help.check.js`, etc.) are static and do not cover all generic phrasing conventions (e.g. `"ここをクリック"`, `"詳しくはこちら"`, bare `"→"`).

### Recommended fixes (priority order)

1. Add `fasttext-langid` for per-element language detection to eliminate `lang` drift.
2. Upgrade `ja_core_news_sm` → `ja_core_news_lg` in `sensory_auditor.py`.
3. Replace CJK character-class stripping with SudachiPy morpheme-level stop-word filtering.
4. Extend `SENSORY_WORDS` with Japanese sensory terms.
5. Normalize half-width katakana via `unicodedata.normalize('NFKC', text)` before all NLP steps.
6. Expand Node JA keyword seed lists for link-purpose, help, error-suggestion, error-prevention checks.

For implementation detail see [Japanese Language Support](/internals/japanese-language-support).
