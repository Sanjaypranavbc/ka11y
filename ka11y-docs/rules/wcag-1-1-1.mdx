## What it checks

WCAG 1.1.1 requires that all non-text content has a text alternative. ka11y goes far beyond checking that `alt` is present — it uses the **Unified Accessibility Pipeline** and ML classification to validate whether the alt text is **semantically appropriate** and not redundant.

## How it works (Unified Pipeline)

The Unified Pipeline evaluates images in their full DOM and visual context:

1.  **Context Extraction**: `ElementContextExtractor` captures the image's role, computed styles, and relationship to its parent containers.
2.  **Semantic Enrichment**: `SemanticRelationshipEngine` determines if the image is part of a larger control (e.g., a button or link) that already has an accessible name.
3.  **Visual Analysis**: The image is classified (Logo, Icon, Informative, Decorative) and OCR'd to detect embedded text.
4.  **Policy Evaluation**: `Policy111` applies specific logic based on this rich context.

### False Positive Protection

To reduce noise and ensure high accuracy, the pipeline includes several specific protections:

*   **Functional Redundancy Check**: If an image is inside an already-labeled `<button>`, `<a>`, or `[role="button"]`, it is automatically marked as **PASSED**. WCAG does not require redundant alt text if the container provides sufficient context.
*   **Word-Boundary OCR Matching**: When validating alt text against OCR-detected text, the engine uses word-boundary regex (`\b`) to ensure semantically meaningful matches, preventing naive substring hits (e.g., "search" matching "research").
*   **Decorative Bypass**: Images classified as `decorative` or marked with `role="presentation"` bypass text-of-image tests, correctly allowing for decorative graphics that might contain incidental text.

## Image classification

Before auditing, every image passes through a deterministic classification cascade:

| Category | Examples |
|----------|---------|
| `decorative/decorative` | Background textures, spacer images, `alt=""` |
| `decorative/presentational` | `aria-hidden="true"` or `role="presentation"` |
| `informative/succinct_information` | Editorial photos, product images |
| `informative/logos` | Standalone brand logos |
| `informative/icons` | Standalone informational icons |
| `functional/buttons` | Images inside `<button>` |
| `functional/logos` | Logos inside navigation links |
| `functional/icons` | Icons inside clickable elements |
| `functional/images` | Other images inside links |
| `complex/charts` | Graphs, infographics, data visualisations |

## Per-classification rules

<AccordionGroup>
  <Accordion title="decorative — alt must be empty (or image hidden from AT)">
    `alt=""` is the canonical pattern. Any non-empty alt text on a decorative image is a **violation** — it will be read by screen readers unnecessarily. A decorative image **without an `alt` attribute at all** is normally a violation, but it PASSES when the element is programmatically hidden from assistive technology — i.e. `aria-hidden="true"` or `role="presentation"` / `role="none"`. The crawler captures both signals from the DOM and the auditor honours them on the missing-alt branch so the AT-hidden pattern doesn't false-fail.
  </Accordion>
  <Accordion title="informative — alt must describe content (OCR-backed)">
    alt must be non-empty. If OCR detects text in the image, one or more meaningful OCR words should appear in the alt text. If the visible text and alt text do not line up, the alt text is flagged as inaccurate.
  </Accordion>
  <Accordion title="functional/logos — alt must include logo/home (or a brand variant)">
    The alt text must contain `logo`, `logotype`, `wordmark`, `brandmark`, `home`, or a localised equivalent (`ロゴ`, `標榜`, `ホーム`, `トップ`) so screen-reader users understand the image is a navigation landmark. Alts like "Meta Platforms Inc. logotype" and "Acme wordmark" are accepted.
  </Accordion>
  <Accordion title="functional/icons — alt must describe the action">
    The alt text must include "icon" or describe the action the icon triggers. Social brand icons must include the brand name (e.g. "Twitter icon" not just "icon").
  </Accordion>
  <Accordion title="functional/buttons — alt must be an action phrase">
    Validated against a vocabulary of 100+ action words (submit, close, play, pause, delete, download, share, search…). Generic alts like "image" or "click here" are violations.
  </Accordion>
  <Accordion title="complex/charts — alt must be non-empty">
    The image must have a non-empty, non-generic `alt` attribute. The auditor checks that `alt` is present and meaningful. Providing a long description via `aria-describedby` is a **best practice** but is not enforced automatically — manual review is recommended for charts and diagrams.
  </Accordion>
</AccordionGroup>

## OCR pipeline

When `run_ocr: true` (default), ka11y uses **PaddleOCR when available** and falls back to **EasyOCR** when PaddleOCR is unavailable in the running environment:

```text
OCR engine → text regions + confidence → contrast check → category
                                                        ├── with_text
                                                        ├── no_text
                                                        └── button_text / logo_text
```

The detected words are then used to validate whether informative-image alt text reflects the visible text content.

For Japanese submissions (`lang: "ja"`), the OCR/image pipeline runs with Japanese-aware recognition while keeping the same API field names and report structure.

## Common violations

| Violation | Example |
|-----------|---------|
| Missing alt | `<img src="banner.jpg">` — no `alt` attribute |
| Decorative with text | `<img src="divider.png" alt="decorative divider">` |
| Generic alt | `<img src="product.jpg" alt="image">` |
| Logo without "logo" | `<img src="logo.svg" alt="Company Name">` should be `alt="Company Name logo"` |
| Inaccurate alt (OCR) | Image contains "50% OFF" but `alt="sale"` |

## Suggested fix

```html
<!-- Decorative (preferred: explicit empty alt) -->
<img src="divider.png" alt="">

<!-- Decorative (also acceptable: AT-hidden, no alt required) -->
<img src="texture.png" aria-hidden="true">
<img src="ornament.png" role="presentation">

<!-- Informative -->
<img src="product.jpg" alt="Blue running shoes with white sole">

<!-- Logo in nav link (any of: logo / logotype / wordmark / brandmark / home) -->
<a href="/"><img src="logo.svg" alt="Acme Corp logo"></a>
<a href="/"><img src="brand.svg" alt="Meta Platforms Inc. logotype"></a>

<!-- Icon button -->
<button><img src="close.svg" alt="Close dialog"></button>

<!-- Chart -->
<img src="chart.png" alt="Q1 revenue chart" aria-describedby="chart-desc">
<p id="chart-desc">Bar chart showing Q1 revenue of £2.4M, up 12% from Q4…</p>
```

## Known limitations

- **Literal OCR matching** — semantic synonyms (alt "Look up" vs OCR "Search") fail the content-equivalence check.
- **Classifier dependency** — a logo mis-labelled as `informative` bypasses the logo-keyword gate.
- **`<object>` / `<embed>` fallback content** is not traversed.
- **2-letter token coverage** — uppercase abbreviations (e.g. "UI", "AI", "OK") are now extracted directly from the raw OCR output before lowercasing, so they are included in the word-match check. Single-character tokens are still excluded.

## CSS background images (supplementary check)

Images set via CSS `background-image: url(...)` are not reachable by the Python OCR crawler (they are not `<img>` elements), but the Node engine's `custom-background-image-content` check (`ka11y-node/src/custom-checks/background-image-content.check.js`) flags them heuristically:

- Scans every element's computed `background-image` for `url(...)` references.
- Filters out pure gradients, data URIs, tiny (< 24 × 24 CSS px) backgrounds, `aria-hidden`/`presentation` roles, and URLs whose filename hints decoration (`gradient`, `pattern`, `noise`, `texture`, `overlay`, `mask`, `fade`, `blur`, `dot`, `divider`, `separator`).
- Emits `status: "incomplete"` (needs review) when a non-decorative background has no accessible name (`aria-label`, `title`, or text content) on its host element — WCAG 1.1.1 concern.
- Emits a separate `custom-background-image-content-text-image` finding when the filename contains text-indicating keywords (`banner`, `headline`, `title`, `hero`, `cta`, `promo`, `callout`, `masthead`, `heading`, `text`) — WCAG 1.4.5 concern, suggesting real CSS-styled text instead of an image of text.

This is a heuristic filename-based signal, not OCR over the background pixels — treat findings as "needs manual review" rather than hard violations.
