title: "Adding a New WCAG Rule"
description: "Intern-friendly guide for adding a rule in ka11y on the Node side, Python side, and shared language files"
---

This guide is for the real ka11y repo, not a toy example. Use it when you need to add a new WCAG rule, extend an existing one, or add language support for that rule.

The short version:

- Put shared WCAG metadata in `i18n/`
- Put language-specific Node behavior keywords and reason templates in `config/universal.yml`
- Put DOM-only checks in `ka11y-node/src/custom-checks/`
- Put crawler + auditor stages in `ka11y-python/ka11y/`
- If the rule should appear as an optional stage, update `CombinedRequest` in `ka11y-python/ka11y/api/v1/combined/models.py` and the frontend audit config.
- The Node.js engine can now be toggled via the `run_node_audit` flag in the API.

## 1. Pick the correct path first

Do this before you write code.

| If your rule needs... | Start here | Why |
| --- | --- | --- |
| Fast DOM checks on the live page, simple heuristics, or interactive browser actions | `ka11y-node/src/custom-checks/` | Node custom checks already run beside axe-core |
| OCR, image analysis, crawler snapshots, or Python-only auditors | `ka11y-python/ka11y/` | Those stages already live in the Python pipeline |
| Both a live browser check and a crawler/auditor check | both Node and Python | Some rules need a quick DOM signal plus a richer Python report |
| Only translated WCAG labels and suggested fixes | `i18n/rules.yml` and `i18n/locales/<lang>.yml` | Both Node and Python read these files |

Practical rule of thumb:

- Start with Node if the rule can be answered from the current DOM and should come back quickly.
- Start with Python if you need crawling, OCR, rendered geometry, screenshots, or multi-page state.
- Do not create both unless you have a clear reason.

## 2. Shared files you almost always touch

These files are the shared source of truth:

| File | What belongs here |
| --- | --- |
| `i18n/rules.yml` | WCAG ID, level, severity, English name, English description, English suggested fix |
| `i18n/locales/ja.yml` | Japanese `name`, `description`, `suggested_fix` |
| `config/universal.yml` | Node check keywords, thresholds, and localized reason templates |

Important:

- `i18n/rules.yml` is shared by Node and Python.
- `i18n/locales/ja.yml` is only for shared WCAG metadata text, not DOM detection keywords.
- `config/universal.yml` is where Node custom checks should read EN/JA keyword lists and reason templates.
- Do not hardcode new English/Japanese keyword regexes inside JS unless there is no other option.

## 3. Node rule workflow

Use this path for `ka11y-node/src/custom-checks/<rule>.check.js`.

### Step 1: Add the WCAG entry

Edit `i18n/rules.yml` and add the success criterion if it is not already there.

Add:

- `level`
- `severity`
- English `name`
- English `description`
- English `suggested_fix`

Then add the Japanese translation in `i18n/locales/ja.yml`.

Student note:

- You usually do **not** edit Node-specific metadata files for this.
- `ka11y-node/src/utils/rulesLoader.js` and `ka11y-python/ka11y/i18n/loader.py` already read the shared YAML.

### Step 2: Add behavior config and language assets

Edit `config/universal.yml`.

This is the right place for:

- keyword lists such as `en` and `ja`
- thresholds like counts, ratios, or limits
- localized reason templates

Example shape:

```yml
checks:
  my_new_rule:
    trigger_keywords:
      en:
        - "example"
      ja:
        - "例"
    min_ratio: 0.5
    reason_templates:
      fail:
        en: "{count} element(s) failed."
        ja: "{count} 件の要素が失敗しました。"
      pass:
        en: "No issues found."
        ja: "問題は見つかりませんでした。"
```

### Step 3: Create the check file

Create `ka11y-node/src/custom-checks/<rule>.check.js`.

Export these constants:

- `SC`
- `RULE_ID`
- `HELP_URL`
- `MODE` if the check is interactive

Usually the file starts like this:

```js
'use strict';

const {
  getSharedRuleContext,
  getKeywordList,
  renderReasonTemplate,
} = require('./sharedAssets');

const SC = '1.2.1';
const RULE_ID = 'custom-my-new-rule';
const HELP_URL = 'https://www.w3.org/WAI/WCAG22/Understanding/...';
const MODE = 'static';
```

Use the helpers in `ka11y-node/src/custom-checks/sharedAssets.js`:

- `getSharedRuleContext(context)`
- `getKeywordList(checkKey, assetKey, context)`
- `getCheckConfig(checkKey, context)`
- `renderReasonTemplate(checkKey, reasonCode, params, context, fallback)`

Example — adding 1.2.4 (Captions (Live)):

Create `ka11y-node/src/custom-checks/captions-live.check.js` which exports SC = '1.2.4' and RULE_ID = 'custom-captions-live'. The check should heuristically detect live media (data-live attributes, HLS/m3u8, "live" badges, or known embed providers) and verify either <track kind="captions">, populated textTracks, or visible captioning elements on the page. Cross-origin embedded players should be flagged for manual verification.

### Step 4: Return structured `elements`

This is the most important rule for coverage.

If your check finds 20 bad links, 20 bad forms, or 20 bad focus targets, return 20 elements. Do **not** only write a nice summary sentence and hope the mapper will recover the nodes later.

Recommended shape:

```js
return {
  successCriteriaId: SC,
  rules: [{
    ruleId: RULE_ID,
    description: 'My rule description',
    impact: 'serious',
    status: 'fail',
    reason: renderReasonTemplate(
      'my_new_rule',
      'fail',
      { count: violations.length },
      sharedContext,
      `${violations.length} element(s) failed.`,
    ),
    helpUrl: HELP_URL,
    elements: violations.map((item) => ({
      html: item.html,
      element_id: item.id || null,
      tag: item.tag || null,
      selector: item.selector || null,
      target: item.selector ? [item.selector] : [],
    })),
  }],
};
```

Why this matters:

- `ka11y-node/src/utils/axeResultMapper.js` only preserves full flat coverage when `elements` is present.
- If you only return `reason`, the mapper can only guess a few nodes from text, which is lossy.

### Step 5: Decide whether it is static or interactive

- Static checks inspect the DOM without mutating browser state.
- Interactive checks focus, type, hover, click, or otherwise change browser state.

If the check is interactive:

- export `MODE = 'interactive'`
- keep it deterministic
- avoid "stop after first violation" unless the page genuinely becomes unsafe to continue
- if you must stop early, say so in the reason and treat the result as partial coverage in future cleanup

### Step 6: Add or update loading order if needed

Node auto-loads every `*.check.js` file from `ka11y-node/src/custom-checks/`, so you usually do **not** need a manual registry entry.

But if you want clean deterministic ordering, update:

- `ka11y-node/src/custom-checks/index.js`

Specifically:

- `STATIC_ORDER` for static checks
- `INTERACTIVE_ORDER` for interactive checks

### Step 7: Write tests

Add a test file:

- `ka11y-node/tests/custom-checks/<rule>.check.test.js`

Common things to test:

- English path
- Japanese path
- pass case
- fail case
- `elements` array is returned for each failing node
- no hardcoded assumptions about page size or sample order

If your rule relies on flat element mapping, also update or add coverage in:

- `ka11y-node/tests/utils/axeResultMapper.custom-flat.test.js`

### Step 8: Verify locally

Typical commands:

```bash
cd ka11y-node
npm test -- --runInBand tests/custom-checks/<rule>.check.test.js
```

If the rule affects mapper behavior:

```bash
cd ka11y-node
npm test -- --runInBand tests/utils/axeResultMapper.custom-flat.test.js
```

## 4. Python rule workflow

Use this path when the rule needs crawlers, auditors, OCR, rendered layout, or richer post-processing.

### Step 1: Decide between Unified Pipeline or Static Auditor

ka11y now prefers the **Unified Accessibility Pipeline** for any rule that requires DOM context, semantic relationships, or interaction simulation (like focus rings).

| If your rule needs... | Use this path | Why |
| --- | --- | --- |
| Deep DOM context, ARIA resolution, or interactive deltas (e.g. 2.4.7, 2.5.8) | **Unified Pipeline Policy** | Centralized extraction prevents false positives and ensures data consistency |
| Specialized multi-page crawling, non-DOM assets (e.g. Media), or unique viewport scenarios | **Static/Rendered Auditor** | Best for rules that don't fit the standard element-by-element pipeline |

### Step 2 (Option A): Adding a Pipeline Policy

1.  **Create the Policy**: Add a new policy class in `ka11y-python/ka11y/accessibility/pipeline/decisions/policies/policy_X_X_X.py` inheriting from `BasePolicy`.
2.  **Define the Logic**: Implement the `evaluate()` method using the rich `ElementContext` (which includes `semantics`, `visual`, and `interaction` sub-contexts).
3.  **Register the Policy**: Wire the new policy into `ka11y-python/ka11y/accessibility/pipeline/pipeline_stage.py`.
4.  **Formatting**: Ensure any unique verdict codes are handled in `ka11y-python/ka11y/accessibility/pipeline/formatters/evidence_formatter.py`.

### Step 2 (Option B): Adding a Static/Rendered Auditor

Before you create a new crawler, check whether the data already exists in:
*   `ka11y-python/ka11y/crawler/universal_page.py`
*   `ka11y-python/ka11y/crawler/rendered_layout_crawler.py`

1.  **Add/Update Auditor**: Auditors live under `ka11y-python/ka11y/accessibility/rules/`.
2.  **Convert to Findings**: Edit `ka11y-python/ka11y/api/v1/combined/findings.py` to add a converter function.
3.  **Wire the Stage**: Edit `ka11y-python/ka11y/api/v1/combined/stages.py` to call your auditor.
4.  **Register Stage**: Update `active_stages` in `ka11y-python/ka11y/api/v1/combined/runner.py` and `STAGE_WEIGHTS` in `ka11y-python/ka11y/api/v1/combined/constants.py` to ensure the stage is included in the job plan and progress reporting.

### Step 3: Write tests

Common Python test locations:

- `ka11y-python/tests/test_combined_findings.py`
- `ka11y-python/tests/test_runner.py`
- a rule-specific test file such as `test_form_auditor.py`
- a crawler-specific test if extraction logic changed

Typical command:

```bash
pytest ka11y-python/tests -q
```

If you only changed one area, run the smallest relevant test file first.

## 5. How language support works

There are three different language layers in ka11y. Keep them separate in your head.

### Shared WCAG metadata

Files:

- `i18n/rules.yml`
- `i18n/locales/ja.yml`

Used for:

- criterion name
- criterion description
- suggested fix
- severity and level

Read by:

- Node: `ka11y-node/src/utils/rulesLoader.js`
- Python: `ka11y-python/ka11y/i18n/loader.py`

### Node rule behavior and localized reasons

File:

- `config/universal.yml`

Used for:

- EN/JA keyword lists
- thresholds
- reason templates

Read by:

- `ka11y-node/src/custom-checks/sharedAssets.js`

Important:

- New Node rules should read behavior from config.
- Do not spread English/Japanese regexes across many check files.

### Python reasons

Current state:

- Python localizes WCAG names and suggested fixes automatically.
- Python `reason` strings still depend on the individual auditor or converter implementation.

That means:

- if you want localized Python `reason` text, you still need to code that path deliberately
- do not assume Python will automatically read your Node reason templates

### Frontend UI language vs audit language

These are currently different concepts.

UI language files:

- `ka11y-frontend-sdk/src/i18n/translations.ts`
- `ka11y-frontend-sdk/src/i18n/LanguageContext.tsx`

Audit language files:

- `ka11y-frontend-sdk/src/types/audit.ts`
- `ka11y-frontend-sdk/src/components/audit/AuditSidebar.tsx`
- `ka11y-frontend-sdk/src/hooks/useAudit.ts`

Important student warning:

- Changing UI language does not automatically mean the audit/report language changes too.
- When you touch language features, check both paths.

## 6. Adding a brand-new language later

If you add a language beyond English and Japanese, check all of these:

1. Add `i18n/locales/<lang>.yml`
2. Add Node behavior keywords and templates in `config/universal.yml`
3. If frontend UI should support it, extend:
   - `ka11y-frontend-sdk/src/i18n/translations.ts`
   - `ka11y-frontend-sdk/src/i18n/LanguageContext.tsx`
   - `ka11y-frontend-sdk/src/types/audit.ts`
   - language buttons in the header and sidebar
4. If axe-core supports that locale, review:
   - `ka11y-node/src/services/accessibility.service.js`
   - specifically `AXE_LOCALE_ALIASES`

## 7. Common mistakes to avoid

- Do not hardcode English/Japanese regexes in every Node rule.
- Do not return only a summary `reason` when the rule knows the actual elements.
- Do not create a new Python crawler before checking the universal snapshot path.
- Do not add a Python toggle without updating the frontend request type.
- Do not assume UI language and audit language are the same setting.

## 8. Definition of done

Before you call the rule finished, check this list:

- WCAG metadata exists in `i18n/rules.yml`
- Japanese metadata exists in `i18n/locales/ja.yml` if the rule should support `ja`
- Node behavior config exists in `config/universal.yml` if this is a Node custom check
- failing Node checks return structured `elements`
- Python findings include real element data when available
- tests cover English and Japanese behavior
- optional stage toggles are wired end-to-end (update `CombinedRequest` and `runner.py`)
- the report looks correct in the frontend, not just in raw JSON
- `STAGE_WEIGHTS` in `constants.py` is updated for accurate progress reporting
- the stage is added to `active_stages` in `runner.py` based on the request flags
