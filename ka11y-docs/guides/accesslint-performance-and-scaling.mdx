This document details the performance characteristics, bottlenecks, and recommended optimization strategies for running `@accesslint/core` and `@accesslint/jest` within the `ka11y-node` engine at scale.

---

## Benchmark Architecture

To accurately simulate enterprise workloads, we created a comprehensive synthetic benchmark suite (`ka11y-node/scripts/benchmark-accesslint.js`) incorporating:
*   **Complex HTML Scenarios:** Documents containing dense ARIA widget patterns, multi-language/Japanese content, malformed accessibility markup, and Shadow DOM fragments.
*   **Large DOM Stress Tests:** Dynamically generated HTML documents with over 15,000 nodes to measure traversal and memory retention costs.
*   **Concurrent Execution Loaders:** Simulating heavy CI/CD utilization (e.g., 100 simultaneous component scans in a single Node process).
*   **Event Loop Profiling:** Simulating Node.js asynchronous blocking to measure the synchronous toll of deep DOM traversal.

---

## Detailed Validation Report

Our integration stress tests confirm the following:

1.  **Determinism & Rule Stability:** Scans are 100% reproducible. Multiple executions of the same complex DOM structure yield identical violation lists and counts.
2.  **Multilingual Handling:** Full UTF-8 preservation is successful. Japanese (`lang="ja"`) and mixed-language documents are parsed correctly without encoding corruption.
3.  **Shadow DOM Piercing:** The engine successfully evaluates elements inside `<template shadowroot="open">` when properly instantiated via JSDOM.
4.  **Concurrency Safety:** Concurrent scans running within the same Jest worker or Node process do not bleed state. Results remain isolated and accurate.

## Scalability Limits & Bottlenecks

### 1. The Synchronous Event Loop Blockage
The most critical bottleneck identified is that `@accesslint/core` executes its DOM traversal **synchronously**. 

**Metric:** In our Event Loop Block Test, scanning a 15k node document took ~1.9 seconds, resulting in a **100% event loop blockage index** for that duration. 

**Impact:** If `runAudit()` is executed on the main thread of an Express server (`ka11y-node`), it will block all incoming HTTP requests for the duration of the scan. This is unacceptable for high-throughput enterprise deployments.

### 2. Large DOM Traversal Cost
**Metric:** 
*   **Small/Medium DOM (< 1000 nodes):** ~40ms 
*   **Large DOM (15k nodes):** ~1930ms 

**Impact:** Execution time scales linearly with DOM size, but the constant factor is high due to the exhaustive nature of ARIA relationship checks and subtree traversal required by WCAG rules.

### 3. Serialization Overhead
**Metric:** JSON serialization of a large result object (~1.6 KB payload) took less than **0.05 ms**.
**Impact:** Negligible. Network transfer and V8 serialization are not bottlenecks in the reporting pipeline.

## Optimization Opportunities

To mitigate the identified bottlenecks, we recommend the following architectural optimizations:

### 1. Worker Threads for Server Environments
Never run large DOM audits on the main Express thread. Instead, offload `runAudit()` to Node.js `worker_threads`.

```javascript
// Example implementation pattern for ka11y-node controllers:
const { Worker } = require('worker_threads');

function runAuditInWorker(htmlString) {
  return new Promise((resolve, reject) => {
    const worker = new Worker('./accesslint-worker.js', { workerData: { html: htmlString } });
    worker.on('message', resolve);
    worker.on('error', reject);
  });
}
```

### 2. Chunked Auditing for Massive Pages
For pages exceeding 10k nodes, consider breaking the DOM into logical subtrees (e.g., `<header>`, `<main>`, `<footer>`) and auditing them in parallel worker threads, merging the results post-execution. Note that this approach requires careful handling of document-level rules (e.g., WCAG 2.4.2 Page Titled).

### 3. JSDOM Caching in Jest
In CI/CD environments, parsing raw HTML strings into JSDOM objects is computationally expensive. If running multiple tests against the same component state, parse the DOM once in a `beforeAll` block and reuse the `document.body` reference across assertions.

## Profiling Commands

For teams wishing to run their own performance validations against proprietary components, use the following built-in profiling tools:

**Run the Baseline Benchmarks:**
```bash
cd ka11y-node
node --expose-gc scripts/benchmark-accesslint.js
```

**Generate a Flamegraph (V8 Profiling):**
To identify specific rules causing slowdowns in your components:
```bash
# 1. Run the benchmark with V8 profiling enabled
node --prof scripts/benchmark-accesslint.js

# 2. Process the resulting isolate-0x...v8.log file
node --prof-process isolate-*.log > processed.txt
```

**Heap Snapshots (Memory Leak Detection):**
```bash
node --heapsnapshot-signal=SIGUSR2 scripts/benchmark-accesslint.js
# In another terminal window: kill -USR2 <pid>
```

## Enterprise Deployment Recommendations

For organizations deploying `ka11y-node` + AccessLint at scale (e.g., gating hundreds of pull requests per hour):

1.  **Resource Limits:** Allocate at least 1GB of RAM per concurrent worker thread. JSDOM and the accessibility tree are memory-intensive.
2.  **Concurrency Budgets:** Cap concurrent scans based on CPU cores rather than memory. The synchronous traversal is CPU-bound. (e.g., `MAX_CONCURRENT_SCANS = os.cpus().length - 1`).
3.  **Timeout Policies:** Enforce strict timeouts (e.g., 5000ms) on audit execution to prevent malformed, infinitely recursive DOM structures from hanging worker threads indefinitely.
4.  **Jest Sharding:** When running `@accesslint/jest` across thousands of components in CI, utilize Jest's `--shard` flag to distribute the CPU load across multiple CI runner nodes.
